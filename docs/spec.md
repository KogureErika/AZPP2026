# アプリケーション技術要件仕様書

## 1. 概要

本アプリケーションは、社内サポート要員が社内からの問い合わせに効率よく回答するための支援ツールである。  
問い合わせ内容を入力すると、類似した過去事例を検索し、その事例に基づいた回答案を自動生成する。  
サポート要員は生成された回答案を参考に最終回答を作成・登録できる。

---

## 2. 利用者

| 区分 | 説明 |
|------|------|
| 主利用者 | 社内サポート要員（問い合わせ対応担当者） |

---

## 3. 機能要件

### 3.1 問い合わせ入力

- サポート要員は、受け付けた問い合わせ内容をテキストとしてアプリに入力できる。
- 入力欄は自由記述形式とする。

### 3.2 類似過去事例検索

- 入力された問い合わせ内容をもとに、過去の問い合わせ・回答ペアのデータベースを検索する。
- 検索はベクトル類似度検索（セマンティック検索）を用い、意味的に近い事例を上位から提示する。
- 検索結果には、過去の問い合わせ内容・回答内容・類似度スコアを表示する。
- 表示件数は上位 5 件程度とし、設定により変更可能とする。

### 3.3 回答案の自動生成

- 検索で取得した類似過去事例をコンテキストとして、大規模言語モデル（LLM）に入力する。
- LLM は類似事例を参照し、今回の問い合わせに対する回答案を生成して表示する。
- 生成される回答案は日本語とする。
- 生成に使用した参照事例（根拠）を回答案とともに表示する。

### 3.4 最終回答の登録

- サポート要員は生成された回答案を参考に内容を編集し、最終回答を確定できる。
- 確定した最終回答はアプリから登録できる。
- 登録された最終回答は、問い合わせ内容とセットで新たな過去事例としてデータベースに蓄積される（フィードバックループ）。

---

## 4. 非機能要件

### 4.1 パフォーマンス

| 項目 | 目標値 |
|------|--------|
| 類似事例検索のレスポンスタイム | 3 秒以内 |
| 回答案生成のレスポンスタイム | 15 秒以内 |
| 最終回答登録のレスポンスタイム | 3 秒以内 |

### 4.2 可用性

- 稼働時間: 平日業務時間（9:00〜18:00）を基本とし、99% 以上の稼働率を目標とする。

### 4.3 セキュリティ

- アクセスは社内ネットワーク内または VPN 経由に限定する。
- 認証は社内 IdP（Azure AD 等）と連携したシングルサインオン（SSO）を利用する。
- 問い合わせ内容・回答内容は機密情報として扱い、外部 LLM API へ送信する場合はデータ取り扱い方針に従う。

### 4.4 拡張性

- 過去事例データが増加してもベクトル検索の性能が維持できるスケーラブルなベクトルデータベースを採用する。
- LLM は設定変更により差し替え可能なアーキテクチャとする。

## 5. システムアーキテクチャ

```
[ブラウザ (サポート要員)]
        │  HTTP/HTTPS
        ▼
[フロントエンド]
  - SPA (React 等)
  - 問い合わせ入力フォーム
  - 検索結果・回答案表示
  - 最終回答編集・登録 UI
        │  REST API / GraphQL
        ▼
[バックエンド API サーバー]
  - 問い合わせ受付
  - ベクトル検索リクエスト送信
  - LLM API 呼び出し（RAG）
  - 最終回答の DB 登録
        │                    │
        ▼                    ▼
[ベクトルデータベース]    [リレーショナル DB]
  - 過去事例の               - 問い合わせ履歴
    埋め込みベクトル           - 最終回答履歴
    格納・検索                 - ユーザー情報
        │
        ▼
[LLM API (Azure OpenAI 等)]
  - 回答案生成
```

## 6. 技術スタック（候補）

| レイヤー | 技術候補 |
|----------|----------|
| フロントエンド | React + TypeScript |
| バックエンド | Python (FastAPI) または Node.js (Express) |
| ベクトル DB | Azure AI Search / Qdrant / pgvector |
| リレーショナル DB | PostgreSQL / Azure SQL |
| LLM | Azure OpenAI Service (GPT-4o 等) |
| 埋め込みモデル | Azure OpenAI Embeddings (text-embedding-ada-002 等) |
| 認証 | Azure Active Directory (Entra ID) + MSAL |
| インフラ | Azure App Service / Azure Container Apps |

## 7. データモデル（主要エンティティ）

### 7.1 問い合わせ (Inquiry)

| フィールド | 型 | 説明 |
|------------|----|------|
| id | UUID | 問い合わせ ID |
| content | TEXT | 問い合わせ本文 |
| created_at | TIMESTAMP | 受付日時 |
| created_by | STRING | 担当者 ID |
| status | ENUM | 対応状況 (open / closed) |

### 7.2 過去事例 (Case)

| フィールド | 型 | 説明 |
|------------|----|------|
| id | UUID | 事例 ID |
| inquiry_content | TEXT | 問い合わせ内容 |
| answer_content | TEXT | 回答内容 |
| embedding | VECTOR | 問い合わせ内容の埋め込みベクトル |
| created_at | TIMESTAMP | 登録日時 |
| source_inquiry_id | UUID | 元となった問い合わせ ID（任意） |

### 7.3 最終回答 (FinalAnswer)

| フィールド | 型 | 説明 |
|------------|----|------|
| id | UUID | 回答 ID |
| inquiry_id | UUID | 対応する問い合わせ ID |
| content | TEXT | 最終回答本文 |
| registered_at | TIMESTAMP | 登録日時 |
| registered_by | STRING | 登録者 ID |

---

## 8. 主要ユースケースフロー

```
1. サポート要員が問い合わせ内容を入力する
2. バックエンドが問い合わせ内容を埋め込みベクトルに変換する
3. ベクトル DB に対して類似事例検索を実行する
4. 上位類似事例をコンテキストとして LLM に送信し、回答案を生成する
5. 類似事例と回答案をフロントエンドに返却・表示する
6. サポート要員が回答案を確認・編集し、最終回答を確定する
7. 最終回答をバックエンド経由で DB に登録する
8. 登録された最終回答が新たな過去事例として蓄積される
```

---

## 9. 制約・前提条件

- 過去事例データは初期ロードとして既存の問い合わせ対応履歴を投入することを前提とする。
- 外部 LLM API を利用する場合、社内の情報セキュリティポリシーに基づきデータ送信の可否を確認すること。
- 本仕様は初版であり、実装フェーズにおいて技術選定の詳細化・変更が生じる場合がある。
